--- reading -----------------------------------------------------------------------

  - Quality: the three NLLs are on the same 459 tokens, so their
    differences are paired, but with one text there is no interval. Each
    setting ran once; under the same conditions (QT_UPLOAD_SYNC=1, the same
    heat table) section 2's repeats were identical, so the uncertainty is
    taken to be which text, not run-to-run noise. Swapping in a rank
    5-12 expert can lower the NLL of a given token, so ROUTE_J=4's -0.0053
    is not impossible, only not expected on average; it marks how much one
    text can move, not a bound. What would narrow it: more text (several
    files, a few thousand tokens), or per-token NLLs from tf_nll, which
    would give a paired standard error over the scored tokens at no extra
    run.
  - The tok/s of section 1 are single runs, not an A/B, and include the
    full-vocabulary softmax of every scored token; section 2 is the speed
    measurement.
  - Speed: ROUTE_J=4's -1.57 ms/token comes, as ROUTE_J=2's did, from
    cpu-miss (3.83 -> 1.99, ms per decode token) and the misses over the
    run (6463 -> 3203, prompt and decode rows); the other timers' changes
    are not attributed (see the ROUTE_J=2 record's reading).
  - QT_UPLOAD_SYNC: this OFF arm (sync on) reads 17.42, the 3 October OFF
    arm (no sync, build 7549736, otherwise the same configuration) 17.43, the ROUTE_J=2
    record's OFF arm (sync on) 18.37. Different sessions, so the sync's
    own cost is still not measured; these numbers do not suggest a large
    one.

--- what this run did NOT measure ---------------------------------------------------

  - Perplexity on more than one text; ROUTE_J=3 or other M / ALPHA values.
  - The gain without QT_UPLOAD_SYNC=1 (the normal mode).
  - Long generations (residency drift: the tier only sees the experts the
    lever chose).
