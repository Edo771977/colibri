WHAT THIS RUN DOES NOT ADD IS THE COST, and an earlier version of this section
claimed it did. It said "the exchange is free" and "the 100 displaced experts
are ones this prompt does not ask for". Both are withdrawn, the same day, for
three reasons that are all visible in the numbers printed above.

  THE RUN TOUCHES EVERY EXPERT. miss = 10240, and 10240 is the TOTAL number of
  experts -- it is the denominator of the engine's own residency line,
  `resident 6859/10240`. And the two cannot be equal by coincidence: the host
  slot cache is per layer with cap == n_experts (the script passes -Cap 256,
  and a cap below the expert count disables the CUDA tier outright), so no
  slot is ever evicted and each (layer, expert) pair can miss AT MOST ONCE.
  miss equal to the total therefore means each one missed EXACTLY once, i.e.
  every expert is reached. "Ones this prompt does not ask for" is contradicted
  by the figure printed beside it. What the data supports is much narrower:
  reaching the displaced 100 cost at most 0.03 ms/token on the cpu-miss timer,
  which is the bound on ALL misses and so bounds theirs too (see below).

  THE HIT RATE CANNOT SEE THE PLACEMENT. The script reads the line `Expert
  cache hit rate:`, which qwen36.c prints from m.hits/m.miss. Those are
  incremented in expert_get() against m->cache[layer] -- the HOST LRU slot
  cache, sized by the script's -Cap 256. They are not the tier's VRAM
  counters. With cap == n_experts nothing is ever evicted from that cache, so
  the rate is pinned by construction, and the sibling record says so itself
  ("identical by construction"). An unchanged 82.6 % is not evidence about
  what the GPU did.

  THE BOUND ON cpu-miss IS WEAKER THAN IT WAS WRITTEN. An earlier version said
  a mean of 0.00 to two decimals means "no individual run carried one either".
  cpu-miss is a continuous ms/token quantity, not a count -- it reads 4.79 and
  5.06 in qwen36-place-clang-clean-2026-09-20-raw.txt:48 -- so a six-run mean
  below 0.005 bounds the six-run sum below 0.03 and therefore each run below
  0.03 ms/token. Small, and not zero.

So what this run establishes about cost is: displacing 100 experts cost under
0.03 ms/token on the one timer that watches it, in a run that touched all of
them. It does NOT establish that they were not wanted.

And the cost evidence here is WEAKER than the explicit-COLI_PLACE record's,
not stronger. That record read the per-run values from all twelve logs and
also carried `VRAM hit rate 100.0 %, LFRU swaps 0, in all twelve`. This
script captures neither VRAM hit rate nor LFRU swaps, and reports means rather
than per-run values. The four cost numbers above are byte-for-byte the ones
that record already published; this run does not improve on them.

It is an answer about THIS card, THIS prompt and THIS heat table, and the heat
table was warmed on the prompt that is then measured -- the most favourable
point available for the claim that nothing needed was evicted. On an 8 or 12 GB
card, or with flatter routing, the same 100 experts could be ones the run does
want, and the cost would appear in cpu-miss. qwen36_tier.c:310 says the placer
will take the trunk anyway: without a heat table the marginal expert is worth
2*topk/n_experts per byte (0.06 here) and "the trunk always wins".

--- LIMITATIONS ------------------------------------------------------------

Stated because each one is something a reader could otherwise assume:

  - The commits behind the two binaries are NOT recorded. The script prints 16
    hex of each sha256 and the header gives the build recipe, but nothing in
    the output ties PRE to a specific main commit or POST to a specific branch
    commit. The script should print that; it does not.
  - AND THAT UNDERMINES THE "SAME DLL" CONTROL ABOVE. Reusing one coli_cuda.dll
    removes a confounder only if both binaries were built from commits that
    differ by #39 alone. #39 itself touches no CUDA source -- that part is
    verified -- but with neither commit recorded, "the DLL is the same" cannot
    be checked against "the sources differ by exactly the change under test".
    The two limitations are one limitation.
  - The hit rate this record quotes is the HOST expert cache's, not the tier's
    VRAM hit rate, and the script captures neither the VRAM hit rate nor the
    LFRU swap count that the explicit-COLI_PLACE record carried. The cost
    evidence here is weaker than that record's, not stronger; see the section
    on what the placer decided.
  - attnproj 10 is the MAXIMUM over the six runs of the arm, not a per-run
    figure. What is established per run is that every POST run placed more
    than zero (the warning never fired) and every PRE run placed exactly zero
    (the guard would have thrown).
  - budget, expert count, hit rate and cpu-miss are MEANS over six runs. The
    script does not print them per run, so "identical in every repetition" is
    not established here the way it was in the explicit-COLI_PLACE record,
    where the per-run values were read from all twelve logs.
  - (shared) and (router) are missing for session 1, as described above.
  - The per-phase rows are arm means over six runs; there are no error bars.
  - Nothing here measures prefill. The fused GEMV is mounted only at S == 1.
