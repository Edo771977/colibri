--- what the script refused to let through ---------------------------------

Checked once per invocation, at the top:

  - COLI_CUDA_PROFILE / PROF / COLI_GRAPH_DIAG inherited from a parent shell.
    Any of them disarms the expert graph or inflates the timers. This one
    FIRED FOR REAL: a first attempt was refused on COLI_GRAPH_DIAG=1, and the
    numbers it would have produced were never taken.
  - the two binaries being byte-identical.

Checked per run, in every one of the twenty-four:

  - the PRE arm placing any attnproj at all. It cannot without the patch, so a
    nonzero count means the wrong binary was copied. It did not fire, in either
    session: all twelve PRE runs placed 0.
  - the POST arm placing none. That is a RESULT, not a fault, so the script
    warns instead of throwing. It did not fire either: all twelve POST runs
    placed more than zero.
  - "attnproj could not be fused or uploaded" -- bytes charged to the expert
    budget for a matrix that never reached the GPU. Did not fire.
  - a missing "step() total" line, i.e. COLI_TIMERS not taking effect.
  - the CUDA tier failing to come up, which on a wrong cap would put the whole
    engine on the CPU and make both arms identical.

The heat table is frozen: warmed once with the PRE binary, cached in
heat.frozen.bin, and restored before every single run. If it drifted between
arms the comparison would be measuring residency, not the placer.

The script only performs that warm-up when heat.frozen.bin is ABSENT, so if the
file survived between the two sessions then both sessions ran on the same
frozen heat. The output does not say whether it did, and this record does not
assume either way.

That is the question the explicit-COLI_PLACE record could not answer, and the
answer is that on this card the exchange is free.

It is an answer about THIS card, THIS prompt and THIS heat table, and the heat
table was warmed on the prompt that is then measured -- the most favourable
point available for the claim that nothing needed was evicted. On an 8 or 12 GB
card, or with flatter routing, the same 100 experts could be ones the run does
want, and the cost would appear in cpu-miss. qwen36_tier.c:310 says the placer
will take the trunk anyway: without a heat table the marginal expert is worth
2*topk/n_experts per byte (0.06 here) and "the trunk always wins".

--- LIMITATIONS ------------------------------------------------------------

Stated because each one is something a reader could otherwise assume:

  - The commits behind the two binaries are NOT recorded. The script prints 16
    hex of each sha256 and the header gives the build recipe, but nothing in
    the output ties PRE to a specific main commit or POST to a specific branch
    commit. The script should print that; it does not.
  - attnproj 10 is the MAXIMUM over the six runs of the arm, not a per-run
    figure. What is established per run is that every POST run placed more
    than zero (the warning never fired) and every PRE run placed exactly zero
    (the guard would have thrown).
  - budget, expert count, hit rate and cpu-miss are MEANS over six runs. The
    script does not print them per run, so "identical in every repetition" is
    not established here the way it was in the explicit-COLI_PLACE record,
    where the per-run values were read from all twelve logs.
  - (shared) and (router) are missing for session 1, as described above.
  - The per-phase rows are arm means over six runs; there are no error bars.
  - Nothing here measures prefill. The fused GEMV is mounted only at S == 1.
