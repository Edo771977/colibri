--- what the script refused to let through ---------------------------------

Three guards, each of which fired at least once during development and each
of which would otherwise have produced a plausible, wrong number:

  - COLI_CUDA_PROFILE inherited from a parent shell. It disarms the expert
    graph and inflates every dense timing. A run with it set looks normal.
  - cap != n_experts. The CUDA tier then disables itself (qwen36_tier.c:499)
    and the whole engine runs on the CPU at 4.16 tok/s; COLI_PLACE places
    nothing, both arms are identical, and the delta is a clean zero.
  - the B arm not actually placing. The guard reads the count back from the
    engine's own announcement (qwen36.c:1533) rather than trusting that
    COLI_PLACE was honoured. It caught a defect in the script itself, where
    $B (the COLI_PLACE string) and $b (a millisecond figure) turned out to be
    the same PowerShell variable -- names there are case-insensitive -- so
    from the second repetition the engine was handed COLI_PLACE=22.6295541977823.

CORRECTION, same day. An earlier version of this file printed two budget
lines here as "A" and "B":

  A  budget 13.76 GB for experts, resident 7805/10240
  B  budget 12.09 GB for experts, resident 6859/10240

They are not the two arms. The 12.09 figure is from attnproj-B-r1.log; the
13.76 is from attnproj-B-r2.log, which is the run the $B/$b variable collision
corrupted -- it was handed COLI_PLACE=22.6295541977823, placed NOTHING at all,
and logs "0.00 GB trunk". So the second line is not arm A, it is a run with no
trunk placement whatsoever, and the 946-expert difference between them is
mostly the other five components, not attnproj's 189 MB. The comparison was
fabricated from a broken log and is withdrawn.

What survives is what the six-repetition summary measured directly and what
the claim actually rests on: cpu-miss 0.00 and the same hit rate in both arms.
A real per-arm budget comparison needs the A-arm logs and is not in this file.

So on a 16 GB card at this context and this heat table, the displaced experts
are ones the run does not ask for. That is a property of this card and this
prompt, not of the change: on a smaller card, or a workload whose routing is
flatter, the same 189 MB could displace experts that ARE missed.

And the placer will NOT stop that. An earlier version of this file, and of the
comment in qwen36.c, said the budget arithmetic decides. It does not, and
qwen36_tier.c:309 says so in the placer's own words: without a heat table the
marginal expert is worth 2*topk/n_experts per byte (0.06 here) and `the trunk
always wins`. With heat it takes a marginal expert routed on more than every
second token; on an int8 container the clamp makes even that unreachable. So a
small card takes these 189 MB too, and pays in cpu-miss.

That is not new with this change -- lmhead, dnproj, dnout and attnout have
behaved this way since they were offered -- and it is not what this run
measured, which was a 16 GB card where nothing was missed. It is written here
because the claim that a budget protects the small card was made in this
file and in the source, and was wrong. The only way out is COLI_PLACE=off or
an explicit list, and naming any one component switches auto off for all of
them.
