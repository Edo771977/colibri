--- what the script refused to let through ---------------------------------

Three guards, each of which fired at least once during development and each
of which would otherwise have produced a plausible, wrong number:

  - COLI_CUDA_PROFILE inherited from a parent shell. It disarms the expert
    graph and inflates every dense timing. A run with it set looks normal.
  - cap != n_experts. The CUDA tier then disables itself (qwen36_tier.c:499)
    and the whole engine runs on the CPU at 4.16 tok/s; COLI_PLACE places
    nothing, both arms are identical, and the delta is a clean zero.
  - the B arm not actually placing. The guard reads the count back from the
    engine's own announcement (qwen36.c:1533) rather than trusting that
    COLI_PLACE was honoured. It caught a defect in the script itself, where
    $B (the COLI_PLACE string) and $b (a millisecond figure) turned out to be
    the same PowerShell variable -- names there are case-insensitive -- so
    from the second repetition the engine was handed COLI_PLACE=22.6295541977823.

The spread is not symmetric between the arms, and that is worth recording:

  A  29.86 .. 30.61   range 0.75 ms   (2.5 % of the mean)
  B  23.09 .. 26.29   range 3.20 ms   (12.7 %)

Generic system load would hit both arms, and would hit A first, since A is the
one doing more work on the CPU. Instead the variance sits almost entirely in
the arm with more work on the GPU. That points at the card -- clocks, thermals,
something else contending for it -- rather than at background processes, and it
argues for quoting the worst of the six as an observed floor rather than
leaning on the median alone.

In B it is also not scatter: 18.4, 19.8, 20.6, 21.0, 20.0, 20.3 on step()
total rises for four repetitions and then settles. ABBA cancels a drift common
to both arms; it does not cancel one that lives in a single arm, and this one
does -- the odd repetitions (B second, so penalised by a common drift) show
LARGER deltas than the even ones, which is the opposite of what a common drift
produces.

The worst reading of that -- free VRAM falling across the session, so the arm
with 189 MB less headroom starts evicting experts it needs -- is EXCLUDED by
the logs: free VRAM reads 14.8 GB in all twelve runs, the budget is identical
within each arm, and hit/miss counts are identical across all twelve. Whatever
the drift is, it is not residency. Clocks, thermals or another GPU client
remain; none has been investigated.

Repetitions 3 and 4 report identical figures to the centesimo in both arms.
Two independent runs agreeing exactly is possible at two decimals of tok/s and

Three explanations, none of them tested, listed weakest claim first because
the honest answer is that the spillover is not attributed.

  (a) It is drift, not signal. qwen36-place-clang-clean-2026-09-20-raw.txt
      measures shared +0.19, router +0.28 and cpu-miss +0.27 between arms at
      IDENTICAL residency on this toolchain, and concludes "the cause is a
      property of the binary, and it is not known". lm_head -0.43 and
      moe_total -0.19 are that size. The breakdown above is also a single
      repetition, with no error bars. This explanation needs no mechanism and
      should be ruled out first.
  (b) Host memory bandwidth: the staging copies of every placed GEMV cross
      host memory, and attnproj on the CPU was reading 189 MB/token of it.
      This is the SAME hypothesis docs/qwen36-cuda-tier.md wrote for the SAME
      unexplained spillover after the dnout/attnout measurement on 19
      September, and it has not been tested since. Writing it twice does not
      make it evidence; it makes it a debt.
  (c) Launch latency and OpenMP, not bandwidth. Removing attnproj from the CPU
      also removes 10 parallel regions per token and stops 16 spinning threads
      from competing with the driver's submit thread. The repo has priced both
      (54 us per region; ~275 ms of a gcc "kernel time" that was really the
      host failing to feed the card).

An internal clue that (b) is not sufficient even for the main row: the byte
model predicts 189 MB at 55.03 GB/s = 3.4 ms of CPU bus, and the measured
attention delta is -3.83 -- in an arm where that timer also carries a new GPU
round-trip. The saving exceeds the byte model where the byte model should be
strongest.

One profiled pass per arm with per-site dense_stats separates them: if it is
bandwidth, h2d/d2h of lm_head and dnproj fall; if it is launch or clock, the
kernel window falls with h2d/d2h flat. Rerunning arm A alone with
KMP_BLOCKTIME=0 discriminates (c). Half an hour of work, not done.

The rest of this paragraph stands as written. It is a property of this card
and this prompt, not of the change: on a smaller card, or a workload whose routing is
flatter, the same 189 MB could displace experts that ARE missed. And the heat
table was warmed ON THE PROMPT THAT IS THEN MEASURED, which is the most
favourable point available for the claim that nothing needed was evicted --
the same caveat docs/qwen36-cuda-tier.md wrote for the 19 September run
("a heat table warmed on the prompt, i.e. the favourable end").

And the placer will NOT stop that. An earlier version of this file, and of the
comment in qwen36.c, said the budget arithmetic decides. It does not, and
qwen36_tier.c:310 says so in the placer's own words: without a heat table the
marginal expert is worth 2*topk/n_experts per byte (0.06 here) and `the trunk
always wins`. With heat it takes a marginal expert routed on more than every
second token. So a small card takes these 189 MB too, and pays in cpu-miss.

An earlier version of this paragraph added that on an int8 container the clamp
made refusal unreachable at all. False, and false the same way as the claim it
replaced: auto_displaced_value sums over k = ceil(bytes/exp_bytes) marginal
experts, so the ceiling on `lose` is k*exp_bytes, above `bytes` unless bytes is
an exact multiple -- a SMALL offer is refused easily. The true statement is
about this offer's size: attnproj is 18.9 MB against 1.80 MB an expert, k = 11,
and refusal would need a mean p above 0.95 across eleven marginal experts.

That is not new with this change -- lmhead, dnproj, dnout and attnout have
behaved this way since they were offered -- and it is not what this run
measured, which was a 16 GB card where nothing was missed. It is written here
because the claim that a budget protects the small card was made in this file
and in the source, and was wrong. The only way out is COLI_PLACE=off or an
explicit list, and naming any one component switches auto off for all of them.

--- what this run did NOT measure ------------------------------------------

The diff this record justifies opens attnproj to the AUTOMATIC placer. Both
arms here ran with an EXPLICIT COLI_PLACE, which switches auto off entirely.
So arm A is not today's default and arm B is not tomorrow's: under auto,
auto_place reprices everything, and the extra 189 MB compete with experts
through auto_displaced_value in a way no run here exercised. The unit test
covers that the placer takes attnproj on attention layers and leaves DeltaNet
alone, but on a toy model with no budget under pressure.

The measurement that would close this is a pair of runs with COLI_PLACE UNSET,
pre-PR binary against post-PR, same discipline. It has not been done, and this
record does not claim it has.
