COLI_CUDA_DENSE_PINNED: pinned host staging for the resident dense GEMV
=======================================================================
RESULT: the premise was WRONG. Pinned staging makes the token SLOWER, in
both modes, 6/6 repetitions each. Keep it off. The finding is worth more
than the change would have been.

2. THE PROFILE: THE MECHANISM WORKED, AND IT DID NOT HELP
---------------------------------------------------------

  COLI_CUDA_PROFILE=1, 5224 dense calls over 64 tokens, one run per arm.
  Residue = wall - h2d - kernel - d2h, i.e. launch and synchronisation.

  arm    h2d    kernel    d2h    residue    wall
  m0    140 ms   640 ms   171 ms    39 ms   990 ms
  m1    186 ms   604 ms   140 ms    83 ms  1013 ms
  m2    118 ms   607 ms    34 ms   160 ms   919 ms

  Mode 2 did precisely what it was built to do. The D2H collapses from
  171 ms to 34 ms (-80 %): with pinned memory the copy is genuinely async,
  so the event window measures the transfer instead of a wait. The wait did
  not vanish, it MOVED -- into the residue, 39 -> 160 ms, which is the one
  cudaStreamSynchronize. Transfers plus residue: 350 -> 312 ms.

  And the token got 2.00 ms WORSE.

  DISCIPLINE NOTE: the profile pass and the A/B are different runs (64 vs
  128 tokens, events on vs off). No arithmetic across them is valid here.
  Each block above is read on its own.


3. WHY THE PREMISE WAS WRONG
----------------------------

  Written down before the run, in the commit message and the docs:

      "mode 1 should be worth roughly zero. It removes a small copy and
       nothing else."

  It is +1.60 ms/token. That is not noise and not zero, and the failure is
  the useful part of the day.

  The h2d column says what happened: 140 -> 186 ms in m1, a 33 % INCREASE
  from the arm that is supposed to be doing strictly less work.

  CUDA's documented behaviour for a pageable host-to-device cudaMemcpy is
  that it returns once the bytes have been copied into the driver's staging
  buffer -- the DMA to the device need not have completed. Every dense call
  on this path is S=1, so xb is 8 KiB, well inside that window.

  So the two "synchronous pageable copies" this patch set out to remove
  were not both synchronous. The H2D was effectively fire-and-forget, and
  the driver's hidden staging copy was not a cost: it was buying asynchrony
  for free, on an 8 KiB payload where the copy is cheaper than the wait.
  Pinning the buffer removed the staging copy and, with it, the early
  return -- so the call now genuinely waits for the DMA.

  Mode 2 restores asynchrony explicitly and still loses, by a further 0.40.
  A blocking cudaStreamSynchronize per call, 81.6 times a token, against
  16 OpenMP threads spinning under OMP_WAIT_POLICY=ACTIVE, is not obviously
  cheaper than the driver's own early return. This run does not separate
  that from the other candidates and does not pretend to.


4. WHAT THIS CHANGES
--------------------

  Kept, off by default, as the B arm for a fact worth not re-deriving:
  on this path the pageable copy is the fast one.

  It also retires the hypothesis that opened the day. The 4.48 ms/token
  measured outside the dense kernels is real, but it is not two removable
  copies. Whatever it is, staging is not the lever.

  The next lever remains what the previous record already named, now with
  one more arm ruled out: FEWER driver calls, not faster ones. 81.6
  round-trips a token is the floor of this design -- batching the placed
  GEMVs, or a graph over the dense trunk the way COLI_CUDA_GRAPH does for
  the expert group.
