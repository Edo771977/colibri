3. THE MODEL THAT EXPLAINS ALL THREE ZEROS
------------------------------------------

The MoE phase is

    issue  +  max(CPU window, GPU group)  +  residue

where the CPU window is the shared expert plus the real misses, and `take`
is what is left of the GPU group after the CPU finishes covering it. take >
0 in every measurement taken today, which says the phase is GPU-BOUND and
the CPU has idle time inside it.

Every lever tried lands in that slack:

  - grouped_down_g4r (#30): GPU group -1.9 ms/token. take 0.53 -> 0.33,
    moe_total unchanged. The saving is capped by how far take can fall, and
    the kernel's own SM contention then cost +1.2 ms on the placed dense
    GEMVs, so the token got WORSE.
  - COLI_CUDA_X_BCAST (#34): h2d -20 %, a GPU-side saving of ~0.2 ms.
    Nothing, for the same reason.
  - COLI_CUDA_GRAPH (this one): issue -0.61, a CPU-side saving. It converts
    to take, one for one. Nothing.

The map this session started from was wrong in a specific way, which is the
useful part: `issue` IS CPU on the critical path of the CPU thread, but the
CPU thread is not what the MoE phase waits for. Being on a critical path
and being on THE critical path are different claims, and this record kept
conflating them.


4. WHAT THE MODEL SAYS TO TRY NEXT
----------------------------------

take is 1.14 ms/token with the graph off and 1.86 with it on: that is real
headroom a GPU-side saving can now convert, where in the earlier session
(take 0.53) it could not. And #30's kernel offers ~1.9 ms/token of GPU
saving that was capped at 0.53 when it was measured alone.

So the two levers that each measured zero are predicted to interact:

    COLI_CUDA_GRAPH=1 makes take bigger (more room)
    COLI_CUDA_DOWN_ROWS=4 makes the GPU group smaller (fills the room)

with #30's contention cost (+1.2 ms on dn-sub proj, norm+out and lm_head)
subtracted. Net estimate: -0.6 ms/token, marginal, and the sign depends on
whether the contention cost survives when the launches are batched.

A 2x2 over {GRAPH 0,1} x {DOWN_ROWS 0,4} tests this directly. It is the
first experiment this session where the prediction comes from a model fitted
to measurements rather than from a shape argument.

6. TWO FLAWS IN THE MEASUREMENT ITSELF
--------------------------------------

The profiled pass reported [NON VALIDO] for graph=1. That is the script's
fault, not the engine's: COLI_CUDA_PROFILE disables the graph by design, so
the absence of the announcement there is expected. A guard that cries wolf
is how a real one stops being read; fixed.

step() was noisier this session than the effect being measured: the graph=0
arm spread 1.50 ms (6 %) and one pair contributed 1.60. The `issue` result
is solid on its own (six pairs, tight, same sign) and the take transfer is
what carries the conclusion -- but any future claim about step() on this
path needs more repetitions than six.
