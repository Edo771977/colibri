Qwen3.6-35B-A3B: heat-table gain, first run of the #51 tool on the real engine.
27 September 2026.

c/tools/misure-heatfile.ps1 was reworked over ten review rounds in #51 and
merged as 8a074f21. In review it was run only against simulated engines on
Linux. This is its first run on the operator's machine, with the real
engine, the GPU and the documented launcher. The run started about six
minutes before the merge (executable 07:48:45 local, merge 07:55:06 +02:00;
its end time is not in the output), on the branch tip, whose script is the
same file that was merged (see "Script" below). It had two questions to
answer before the merge:

  1. Do the six runs of the SAME arm generate the same text? The tool
     refuses the run if they do not; if they diverged systematically it
     would refuse every run of this configuration.
  2. Do COLD and CROSS generate the same text? Nothing in the earlier
     records says. The tool declares the answer without refusing.

Both answers are yes, for this prompt pair, N_NEW=128 and this build.

--- three refused attempts -------------------------------------------------

The tool stopped three times before the run below. Each was a real
condition of the machine, and each message named it:

  1. COLI_GRAPH_DIAG=1 in the environment (the environment guard). No C
     source on main reads this variable. The diagnostic commit 6652f6b7,
     on the branch claude/graph-diag and never merged, reads it in
     c/backend_cuda.cu, that is in coli_cuda.dll; the DLL of this run is
     not that build (below). The variable was absent at the next attempt.
  2. CUDA_EXPERT_GB=12 in the environment (the environment guard). The
     engine reads this one: it is the per-device allowance for tier and
     trunk (c/qwen36_tier.c:607). Removed with `set CUDA_EXPERT_GB=`, so the
     allowance is the engine's default, per main's source free VRAM minus 1
     GB (:612-618). That value is printed in the per-run logs, not in the
     output below.
  3. ".\qwen36_clang.exe NON e' la copia di qwen36.exe (sha256
     E2AB428B44E9CAD5 contro E0345C330BE51603)" (the provenance guard).
     Fixed by the rebuild above.

The guard lists every suspect variable at once, and attempt 1 did not list
CUDA_EXPERT_GB. So the environment of attempt 2 differed from that of
attempt 1 by more than the removal of COLI_GRAPH_DIAG; how is not known.

The successful run's stamp reads allow-env=nessuna: the environment guard
found no suspect variable and no exemption was used.

The DLL's date, 2026-09-21 20:46:01 local time, falls about half an hour

and pasted:

The check was run after the measurement and prints no hash: that the file
read is the DLL of the run (sha256 0D57602B...) is assumed, not shown. No
command given rebuilt it, and the Makefile does not make it a prerequisite
of qwen36.exe.

"BeginCapture FALLITA" is part of a string literal of 6652f6b7, in an
fprintf under #if COLI_GPU_HAS_GRAPH, which is 1 in every CUDA build
(c/backend_gpu_compat.h:120); no source file on any other branch of the
repository contains it. "[CUDA] invalid device" is a string literal of
c/backend_cuda.cu present in the oldest version in this clone (aa87ff5f), on
main and on claude/graph-diag, outside every #if on both of the latter: it
is the control that the reading works on this file. A build of 6652f6b7
would contain both.

An earlier check with findstr is not quoted as evidence: its control
string turned out to sit inside #ifdef COLI_ANS, so its absence said
nothing about findstr.

--- the generated text -----------------------------------------------------

Question 1: the six COLD runs share one hash, and so do the six CROSS runs.
Question 2: the two hashes are the same, 513eed141820d28b, and the tool
printed IDENTICO. The comparison is on stdout as PowerShell reads it,
without a leading [meta] line, with the lines rejoined by LF.

This also shows that the tool separated stdout from stderr on this
launcher. Had stderr lines entered the text, their per-run timings would
have made the six hashes of an arm differ.

The CROSS miss count reads 6240 in some runs and 6241 in others, while the
text is the same in all six: identical text does not imply identical
counters. Nor does it imply identical arithmetic: the arms compute
different experts on the CPU and on the GPU, and the text only says that
the decoded strings came out the same. Not even the token sequences are
shown to be the same: two different sequences can decode to the same
text.
