Summary:

  1. Two launches of each kernel were profiled in decode (sixth token,
     --set full, --clock-control none). The first hidden launch ran with
     the GPU still at idle clocks (SM 270 MHz, DRAM 404 MHz; 647 us) and is
     discarded; the second hidden launch and both down launches ran at
     2.74 / 2.52 GHz SM and 10.23 GHz DRAM:
       hidden (512 x 1 x 8 blocks of 256): 44.0 us, DRAM throughput 33.4 %
         of peak (218 GB/s), Compute (SM) throughput 69.5 %, LSU the most
         used pipeline at 69.4 %, issue slots busy 60.5 %, achieved
         occupancy 93.8 %, 19,261,568 executed warp instructions; L1TEX
         scoreboard stalls 43.4 % of the 17.9 cycles between issues.
       down<4> (512 x 1 x 8 blocks of 256): 26.1 us, DRAM 28.3 % (185 GB/s),
         Compute (SM) 58.5 %, LSU 58.5 %, issue slots 58.5 %, achieved
         occupancy 76.6 %, 10,129,408 executed warp instructions.
     Both kernels use a third of the memory bandwidth while the LSU and the
     issue slots are well used: they issue more instructions than the bytes
     they read need. The durations match the moe4 trace (hidden median
     43.9 us, down 23.5 us; docs/experiments/qwen36-group-zc-out-2026-10-10-
     raw.txt) to within the profiler's isolation.
  2. Where the instructions go, read from the SASS of backend_cuda.cu built
     in the cloud session with nvcc 12.0 for sm_89 (the operator's DLL is
     built with CUDA 13.4; the code generated there may differ): the inner
     loop of grouped_hidden_g4_dual is 101 instructions per iteration, about
     40 of them the two runtime integer divisions i/ggs and i/ugs that pick
     the scale; x is read with two scalar loads; the reduction is eight
     shared-memory steps with a barrier each. Four iterations per thread
     (D = 2048: 1024 bytes per row, 256 threads), plus the reduction and the
     prologue, make about 590 instructions per warp, which is what the
     profile counts: 19,261,568 / (4096 blocks x 8 warps) = 588. The down
     kernel's loop is 133 instructions per iteration at R=4, with one
     division.
  3. COLI_CUDA_GS64=1 (this change): versions of both kernels with the
     group size 64 compiled in (the division becomes a shift), x read as one
     float2, and the last five reduction steps as warp shuffles; the same
     arithmetic in the same order, so the rows are bitwise those of the
     generic kernels. Same compiler, same flags: the hidden loop is 49
     instructions per iteration (from 101), the down<4> loop 92 (from 133);
     the floating-point operations of both loops have the same form (the
     weight times x, then an FMA by the scale into the accumulator).
     Hypothesis: if the instruction count is what limits them, both kernels
     get shorter; if it is memory latency, less so. Not measured.

in the NVIDIA Control Panel. Nsight Compute 2026.3.0 writes the report as

The keep-alive was off (a kernel that spins under a profiler that
serialises kernels), and the zero-copy variants off (the two kernels are
the same with or without them). An earlier run of the same command, before
the counters were allowed, printed "[qtier] group_stats: 1600 calls" (25
prompt + 15 decode positions x 40 layers): 3200 matching launches, so
--launch-skip 2400 lands in decode.
