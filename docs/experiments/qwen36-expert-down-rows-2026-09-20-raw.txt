Three readings, in order of how much they matter.

(a) THE KERNEL REALLY IS FASTER, and `take` says so independently of
    group_stats: 0.53 -> 0.33 ms/token at R=4, 0.28 at R=8. Two separate
    measurements agree that the expert group finishes earlier.

(b) AND IT BUYS NOTHING, because moe_total does not move (8.55 -> 8.57).
    `take` was only 0.53 ms of a 24 ms token to begin with: the expert
    kernels were ALREADY off the critical path, overlapped with CPU work
    that finishes later. 1.9 ms/token of GPU time was freed and had
    nowhere to go.

(c) AND IT COSTS. 91 % of the +1.31 ms regression is three lines --
    dn-sub proj +0.60, norm+out +0.20, lm_head +0.39, sum +1.19 -- and
    those three ARE the placed dense GEMVs (dnproj, dnout, lmhead in the
    COLI_PLACE list), which run on stream 0 concurrently with the expert
    group on ctx->stream.

    The mechanism follows from the kernel's shape. At R=0 the down kernel
    is 16,384 blocks that each read one byte and retire almost at once,
    leaving scheduling slots free for the dense blocks interleaved with
    them. At R=4 it is 4,096 blocks that live four times as long and hold
    4 KB of shared memory each (partial[R][256]), so fewer dense blocks
    fit alongside. The kernel wins its own race and slows down the one
    next to it.

    attnout is also placed, and `attention` barely moves (+0.04) -- so the
    contention is not uniform across the placed matrices. Not explained.


3. WHAT THIS SAYS ABOUT THE EXPERT PATH
---------------------------------------

nsys put grouped_down_g4 at 183 ms and grouped_hidden_g4_dual at 167 ms
against quant_matmul's 247 ms, and that comparison is what motivated this
kernel. It was misleading: expert GPU time is overlapped, dense GEMV time
is on the critical path, and nsys totals cannot tell them apart.

The lever is not the expert kernels. On this configuration the big items are:

  deltanet        7.70   (of which dn-sub proj 3.5, l2n+rec 2.1)
  moe_total       8.55   (router 0.99 + issue 1.76 + CPU window 4.95 + take 0.53)
  attention       5.68

CAREFUL WITH `cpu-miss`. Despite the name it is not the cost of the misses:
it is the whole window between qt_issue and qt_take (qwen36.c, `_q1` to
`_q2`), and the SHARED EXPERT is computed inside it on purpose, to overlap
with the GPU groups. So 4.95 = shared 4.17 + roughly 0.78 of actual
CPU-computed misses. The misses cost about 3 % of the token, not the fifth
that the raw counter suggests. An earlier version of this file said the
latter; it was wrong.

What the corrected reading shows is more useful anyway: the CPU window
(4.95) and the GPU expert group are NEARLY BALANCED -- take is only 0.53,
so the GPU finishes 0.53 ms after the CPU is done with it. That is why this
kernel bought nothing, and it also says speeding up the CPU side alone would
run into the GPU within half a millisecond. The two have to move together:
cut the shared expert AND keep a faster down kernel, and both start paying.
That is a prediction, and it is the reason the toggle stays in the tree.


4. WHY THE KERNEL STAYS IN THE TREE, OFF
----------------------------------------

It is bitwise identical to grouped_down_g4 (tests/test_grouped_down_rows_
cuda.cu, memcmp on eight shapes), so it costs nothing while unset, and it
is the only way to reproduce the finding above. It also stops being a bad
idea the moment the expert path lands on the critical path -- a larger
batch, or a configuration where cpu-miss is fixed and the GPU becomes the
bottleneck. Today it is neither of those, and the default reflects that.
